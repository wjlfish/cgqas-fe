# 创高题库检索

> 本项目仅用于复习学习创高体育 App 内的学习题目。
> **开发者不提倡也不建议任何同学在考试时使用此题库。**

在线地址：[https://cgtk.wjlo.cc](https://cgtk.wjlo.cc)

## 这是什么

一个面向「四川大学创高体育理论考试」的题库检索工具。输入关键词即可查到题干、
选项与标准答案，支持按科目、题型筛选，以及随机练习与即时判分。

**后端为 PHP + MySQL，前端为原生 HTML/CSS/JS，无构建步骤、无框架、无外部依赖。**

## 功能

- **检索**：题干/答案全文匹配，关键词高亮，支持科目与题型组合筛选
- **练习**：按科目随机抽题，判断题与单选题点击即判，多选题需确认
- **统计**：题库总量、题型分布、各科题量
- **双主题**：纸 / 墨，跟随系统或手动切换
- **键盘优先**：`/` 聚焦搜索，`Esc` 清空
- **移动端适配**：390px 下工具栏折叠为两行，首屏仍可见 6 条结果

## 技术架构

```
浏览器 (原生 JS, 无构建)
   │  X-CG-Token: HMAC 令牌
   ▼
api.php ── 路由 / 校验 / 限流 ──► MySQL
   │
   ├── lib/db.php         PDO 连接
   ├── lib/ratelimit.php  限流与反爬
   ├── lib/admin.php      审阅页鉴权
   └── lib/response.php   统一 JSON 输出
```

## 目录结构

## 部署

前置：PHP 8.0+ (pdo_mysql、mbstring、openssl)、MySQL 8.0+。

```bash
# 1. 拉代码
git clone https://github.com/wjlfish/cgqas-fe.git && cd cgqas-fe

# 2. 建库建表
mysql -u root -p -e "CREATE DATABASE cgtk DEFAULT CHARSET utf8mb4"
mysql -u root -p cgtk < sql/schema.sql

# 3. 配置
cp lib/config.example.php lib/config.php
#   填入数据库账号、随机 secret、管理口令 admin_key

# 4. 授权目录给 web 用户
chown -R www:www . && chmod -R 755 .
```

Web 根目录指向本仓库根目录即可。`index.php` 为默认入口，
`.htaccess` 已屏蔽 `lib/`、`sql/`、`.git/` 与敏感后缀。

不需要 Node、不需要 npm install、不需要打包。

## 数据说明

**题库数据不在本仓库内。** 仓库只包含程序与表结构。

题目表 `questions` 的字段约定：

| 字段 | 说明 |
|---|---|
| `type` | `判断` / `单选` / `多选` / `填空` / `问答` |
| `stem` | 题干原文 |
| `stem_norm` | 题干归一化后的 SHA1，用于去重（唯一键） |
| `options` | JSON 数组 `[{"key":"A","text":"…"}]`，判断题为 `NULL` |
| `answer` | 判断题存 `正确`/`错误`；选择题存选项字母如 `A`、`AC` |
| `source` | 数据来源标记 |
| `subject_id` | 主科目 |

题目与科目是多对多关系，映射表为 `question_subjects`。

## 安全与反爬

站点是公开的只读检索服务，但题库不能让人整库拖走。为此做了分层设计：

### 第一层 · 令牌与会话

| 措施 | 说明 |
|---|---|
| 令牌校验 | 页面下发 HMAC 令牌(`X-CG-Token`)，无令牌或伪造令牌直接拒绝 |
| 同源校验 | 校验 `Sec-Fetch-Site` / `Referer`，阻断跨站调用 |
| UA 黑名单 | curl、python-requests、HeadlessChrome、scrapy 等命中即封 24h |
| 蜜罐路径 | `action=__trap` 命中即封 24h |

### 第二层 · 枚举门槛

**翻页必须带关键词。** 这是最关键的一条——否则一次空查询加几个科目就能把全库翻完。

| 规则 | 说明 |
|---|---|
| 翻页门槛 | `page > 0` 要求关键词长度 ≥ 2 字，否则 400 |
| 页数上限 | 有关键词时最多翻 10 页，即单次查询最多 200 条 |
| 随机浏览 | 无关键词时改为**随机抽样 20 条**，不返回分页信息，前端只提供「换一批」 |

随机抽样意味着每次拿到的都是不同子集、重复率高。按当前题库规模，
仅靠采样覆盖全库的性价比极低。

### 第三层 · 累计配额

`serve_budget` 表按 IP + 自然日记录累计**返回记录数**（不是请求数）：

| 阈值 | 默认 | 处置 |
|---|---|---|
| 5 分钟内累计返回 | 400 条 | 直接封禁 15 分钟 |
| 每日累计返回 | 1500 条 | 当日拒绝，提示次日再来 |

1500 条约为全库的 21%。单个 IP 一天拿不完，要覆盖全库需要多个出口且逐个受限。
配额按「返回条数」而非「请求次数」计算，正常复习不会触发；用 1 条查询换 20 条数据的爬虫会被快速卡住。

### 第四层 · 频率与行为

| 措施 | 默认 |
|---|---|
| 每分钟请求 | 100 次 |
| 10 秒突发 | 30 次（仅降速，不计违规） |
| 每日请求 | 1200 次 |
| 违规累计 | 5 次封禁 15 分钟 |
| 严重滥用 | 单分钟 > 150 次直接封 24h |
| 翻页枚举 | 5 分钟内翻页 > 40 次封禁 |

限流状态存 `rate_limits`，配额存 `serve_budget`，均按 IP 维度。

### 需要说明的边界

以上措施能挡住随手的脚本和常规爬虫，但**挡不住有大量代理池且愿意投入的人**。
公开检索类服务的本质决定了这一点：接口必须能被正常浏览器调用，就无法在协议层
完全区分人与脚本。上述分层的作用是把「357 次请求拖走全库」变成
「需要多个 IP、多天、且被反复封禁」，让成本远高于收益。

真要再往上加，只有上验证码或登录态两条路，都会伤正常用户的检索体验。
