# 创高题库检索

> 本项目仅用于复习学习创高体育 App 内的学习题目。
> **开发者不提倡也不建议任何同学在考试时使用此题库。**

在线地址：[https://cgtk.wjlo.cc](https://cgtk.wjlo.cc)

## 这是什么

一个面向「四川大学创高体育理论考试」的题库检索工具。输入关键词即可查到题干、
选项与标准答案，支持按科目、题型筛选。

**后端为 PHP + MySQL，前端为原生 HTML/CSS/JS，无构建步骤、无框架、无外部依赖。**

## 功能

- **账号**：手机号验证码登录，免注册，每账号 150 次搜题额度
- **检索**：题干/答案全文匹配，关键词高亮，支持科目与题型组合筛选
- **统计**：题库总量、题型分布、各科题量
- **双主题**：纸 / 墨，跟随系统或手动切换
- **键盘优先**：`/` 聚焦搜索，`Esc` 清空
- **移动端适配**：390px 下工具栏折叠为两行，首屏仍可见 6 条结果

## 部署

前置：PHP 8.0+ (pdo_mysql、mbstring、openssl)、MySQL 8.0+。

```bash
# 1. 拉代码
git clone https://github.com/wjlfish/cgqas-fe.git && cd cgqas-fe

# 2. 建库建表
mysql -u root -p -e "CREATE DATABASE cgtk DEFAULT CHARSET utf8mb4"
mysql -u root -p cgtk < sql/schema.sql

# 3. 配置
cp lib/config.example.php lib/config.php
#   填入数据库账号、随机 secret、管理口令 admin_key

# 4. 授权目录给 web 用户
chown -R www:www . && chmod -R 755 .
```

Web 根目录指向本仓库根目录即可。`index.php` 为默认入口，
`.htaccess` 已屏蔽 `lib/`、`sql/`、`.git/` 与敏感后缀。

不需要 Node、不需要 npm install、不需要打包。

## 数据说明

**题库数据不在本仓库内。** 仓库只包含程序与表结构。

题目表 `questions` 的字段约定：

| 字段 | 说明 |
|---|---|
| `type` | `判断` / `单选` / `多选` / `填空` / `问答` |
| `stem` | 题干原文 |
| `stem_norm` | 题干归一化后的 SHA1，用于去重（唯一键） |
| `options` | JSON 数组 `[{"key":"A","text":"…"}]`，判断题为 `NULL` |
| `answer` | 判断题存 `正确`/`错误`；选择题存选项字母如 `A`、`AC` |
| `source` | 数据来源标记 |
| `subject_id` | 主科目 |

题目与科目是多对多关系，映射表为 `question_subjects`。

账号相关表：`users`（手机号与额度）、`auth_sessions`（登录态）、`sms_codes`（验证码与频控）。

访问 `/admin.php`，用 `lib/config.php` 里的 `admin_key` 登录（HttpOnly + SameSite=Strict Cookie，有效期 7 天）。

面板共 9 个页签：

| 页签 | 内容 |
|---|---|

| **用户** | ID、手机号、已用/额度、状态、注册时间、最后登录、最后 IP；支持按手机号搜索 |
| **访问日志** | `access_logs` 页面级埋点：时间、IP、设备类型、设备型号、UA；支持按设备/IP 筛选 |
| **访客请求** | `request_log` 明细：时间、IP、action、关键词、状态码、耗时、UA；支持按 action / 状态码 / IP 筛选 |
| **检索记录** | `search_logs`：谁在什么时候搜了什么、返回多少题 |
| **短信记录** | `sms_codes`：手机号、IP、校验次数、是否已用、过期时间 |
| **限流封禁** | `rate_limits`（日请求/窗口/突发/违规/封禁到期/验证豁免）+ `serve_budget`（按 IP 的条数额度） |
| **反馈** | 错题申报 / Bug / 点赞 / 评论明细，可按类型与状态筛选。错题类可「查看并改答案」：弹框内可改**题干、选项、答案**，保存后题目同步更新、反馈自动置为已处理，`admin_note` 记下改动内容；也可「删除此题」。点赞类操作是「答谢 / 不管」，答谢后该用户在点赞页会看到答谢语；其余类型「处理 / 忽略 / 重开」 |
| **去重审阅** | 5 类重复题对比与处置（详见下节） |

### 去重审阅

按题干相似度从高到低排列，5 个分类：

| 分类 | 含义 |
|---|---|
| ① 近同题·答案不同 | 题干几乎一样但答案冲突，需人工裁定 |
| ② 近同题·答案相同 | 可安全合并 |
| ③ 仅科目前缀不同 | 差异只在科目名 |
| ④ 内容相近 | 相似度中等，供参考 |
| ⑤ 旧库重复(2026已有) | 旧库题在 2026 题库中有对应，建议整批删除 |

每对可「保留 A 删 B」「保留 B 删 A」「两者都保留」。删除时会把被删题的科目归属并入保留题，
不会丢科目关联。⑤ 类另有批量删除按钮（保留 2026 版）。

> 去重决策记录在 `dedupe_decisions`，已处理的不会再出现。

**注意**：后台面板不对外暴露，前台任何页面都没有指向它的链接。`robots.txt` 已屏蔽。

### 防盗刷设计

这是本次改动的重点，错题申报的检索**没有**另起一套接口：

- 错题申报里的检索直接复用 `action=search`，因此**同样消耗 1 次搜题额度**，
  同样受「关键词 ≥2 字、每页 5 条、最多 10 页」的约束
- 申报本身**不消耗额度**（它是贡献行为），但做了独立频次控制：

| 限制 | 值 |
|---|---|
| 错题申报 | 每用户 20 条/日，每 IP 40 条/日 |
| Bug 反馈 | 每用户 5 条/日，每 IP 15 条/日 |
| 留言评论 | 每用户 5 条/日，每 IP 15 条/日 |
| 点赞 | 每用户仅一次（幂等写入） |
| 同题重复申报 | 7 天内同用户同题只接受一次 |

- 申报接口**只校验题目是否存在，绝不回传题目内容**，
  避免被当成「按 ID 取题」的免费通道绕开额度
- 举报/反馈/评论均要求登录（`login_required`），未登录一律 401

### 错题处理弹框

点击反馈行里的「查看并改答案」，弹框内包含：

| 区域 | 可操作 |
|---|---|
| **题干** | 文本域，可直接改写（上限 2000 字） |
| **选项** | 单选/多选/问答可增删改；序号 A–J，内容上限 500 字 |
| **当前答案 / 修改为** | 判断题用「正确/错误」快捷键，选择题用选项字母键（多选可叠加） |
| **申报信息** | 申报人、时间、问题类型、补充说明、联系方式 |
| **删除此题** | 二次确认后硬删除 |

保存时后端会做这些校验：

- 题干非空、去重（改题干会重算 `stem_norm`，与已有题重复则拒绝并提示冲突题号）
- 选项序号必须为单个字母、不重复、内容非空，最多 10 个
- 答案字母必须存在于该题选项；单选题只能一个字母
- 判断题答案归一化为「正确/错误」（接受 对/错/T/F）

> `stem_norm` = 去掉标点与空白后的 SHA1，例如
> `柔韧指动态或静态动作的范围。` → `561729f58db533bd2ea5d69a9f165446757d2de6`。
> 改题干时必须同步重算，否则唯一键会脏。

### 题目改动归档

所有编辑与删除都会写入 `questions_archive`：

| 字段 | 说明 |
|---|---|
| `question_id` | 题目 ID |
| `action` | `edit` / `delete` |
| `old_json` | 改动前内容（题干、选项、答案；删除时为整行） |
| `new_json` | 改动后内容（删除时为 NULL） |

删除题目时会连带清理 `question_subjects`、`dedupe_pairs`、`dedupe_decisions`，

### 维护注意：不要无条件清空 feedback

`feedback` 表里混着真实用户提交的内容与测试数据。清理时**必须**按测试账号圈定范围，例如：

```sql
DELETE f FROM feedback f
JOIN users u ON u.id = f.user_id
WHERE u.phone IN ('13900006666', '13900007777');   -- 只删测试手机号
```

禁止 `DELETE FROM feedback;` / `TRUNCATE TABLE feedback;`。

误删后的恢复路径（本机 binlog 已开启，`binlog_format=MIXED`）：

```bash

  /www/server/data/mysql-bin.000007 > /tmp/bl.txt

# 找出被删的 INSERT（语句格式，带完整字段）
grep -a 'INSERT INTO feedback' /tmp/bl.txt
```

## 安全与反爬

站点是公开的只读检索服务，但题库不能让人整库拖走。为此做了分层设计：

### 第一层 · 令牌与会话

| 措施 | 说明 |
|---|---|
| 令牌校验 | 页面下发 HMAC 令牌(`X-CG-Token`)，无令牌或伪造令牌直接拒绝 |
| 同源校验 | 校验 `Sec-Fetch-Site` / `Referer`，阻断跨站调用 |
| UA 黑名单 | curl、python-requests、HeadlessChrome、scrapy 等命中即封 24h |
| 蜜罐路径 | `action=__trap` 命中即封 24h |

### 第二层 · 枚举门槛

**翻页必须带关键词。** 这是最关键的一条——否则一次空查询加几个科目就能把全库翻完。

| 规则 | 说明 |
|---|---|
| 翻页门槛 | `page > 0` 要求关键词长度 ≥ 2 字，否则 400 |
| 每页条数 | **5 条** |
| 页数上限 | 有关键词时最多翻 10 页，即单次查询最多 **50 条** |
| 关键词必填 | 无关键词直接拒绝（400 `need_keyword`），彻底取消随机浏览 |

取消随机浏览很关键：此前空关键词会随机抽 20 条，150 次额度就能拿到约 3000 题，
几个手机号即可覆盖全库。现在必须有关键词，只能定向检索。

配合每页 5 条，单账号 150 次额度的理论上限降到 **750 题**（约全库 10.5%），
且需要构造至少 15 个各命中 50 条以上的宽泛关键词才能触及上限。

### 第三层 · 累计配额

`serve_budget` 表按 IP + 自然日记录累计**返回记录数**（不是请求数）：

| 阈值 | 默认 | 处置 |
|---|---|---|
| 5 分钟内累计返回 | 400 条 | 直接封禁 15 分钟 |
| 每日累计返回 | 1500 条 | 当日拒绝，提示次日再来 |

1500 条约为全库的 21%。单个 IP 一天拿不完，要覆盖全库需要多个出口且逐个受限。
配额按「返回条数」而非「请求次数」计算，正常检索不会触发；用 1 条查询换 5 条数据的爬虫会被快速卡住。

### 第四层 · 频率与行为

| 措施 | 默认 |
|---|---|
| 每分钟请求 | 100 次 |
| 10 秒突发 | 30 次（仅降速，不计违规） |
| 每日请求 | 1200 次 |
| 违规累计 | 5 次封禁 15 分钟 |
| 严重滥用 | 单分钟 > 150 次直接封 24h |
| 翻页枚举 | 5 分钟内翻页 > 40 次封禁 |

限流状态存 `rate_limits`，配额存 `serve_budget`，均按 IP 维度。

### 第五层 · 手机号验证登录 + 搜题额度

免注册：手机号 + 短信验证码，未注册的自动建号，无需设置密码。

| 项目 | 默认 |
|---|---|
| 每个账号搜题次数 | **150 次** |
| 登录有效期 | 7 天 |
| 验证码有效期 | 5 分钟 |
| 同号发送间隔 | 60 秒 |
| 同号每日发送 | 5 条 |
| 同 IP 每小时/每日 | 10 / 30 条 |

每次检索消耗 1 次机会；用完返回 403 `quota_exhausted`，前端展示明确提示。
空关键词等无效请求在扣额度**之前**就被拒绝，不消耗额度。

> 随机练习功能已下线：它会成为绕过关键词门槛的整库导出通道，
> 前端入口与 `api.php` 的 `quiz` action 均已移除（调用返回 404）。
额度与用量记录在 `users` 表，登录态为 HttpOnly Cookie + 服务端会话表。

短信走**阿里云号码认证服务**的短信认证接口（`dypnsapi`）：

- `SendSmsVerifyCode` 发送验证码
- `CheckSmsVerifyCode` 平台侧核验

需要在号码认证控制台开通短信认证，并把**赠送的签名名称与模板 CODE** 填进
`lib/config.php` 的 `aliyun.sign` / `aliyun.template`，同时把 `aliyun.mode` 设为
`dypns_platform`。自建签名/模板在该产品下会返回「签名或者模版无效」。

调试可先用 `aliyun.mode = dev`：不真正发短信，验证码写入服务器
`/tmp/cgtk_sms_dev.log`。上线前务必切换。

> 短信会产生费用（按运营商回执计费），因此对发送做了手机号与 IP 双重频控。

### 短信发送前置 · 阿里云验证码 2.0

短信是要花钱的，因此「发送验证码」这一步单独做人机校验（检索本身不需要验证）：

- 客户端：`AliyunCaptcha.js` 弹出式验证，绑定「获取验证码」按钮
- 服务端：`VerifyIntelligentCaptcha` 校验 `CaptchaVerifyParam`，不通过直接拒绝，
  **不会调用短信接口**，因此被拦的请求不产生任何短信费用
- 未配置场景时自动降级为不校验（仅靠手机号与 IP 频控）

启用步骤：

1. 控制台开通[验证码 2.0](https://help.aliyun.com/zh/captcha/captcha2-0/product-overview/)
   （按量 0.005 元/次，或包年包月基础版含 2000 次/天）
2. 新建「接入方式 = Web/H5」的验证场景，拿到 **场景ID（SceneId）**
3. 在概览页拿到 **身份标（prefix）**
4. 填入 `lib/config.php` 的 `captcha2.scene_id` / `captcha2.prefix`，并把 `enable` 改为 `true`

> ⚠️ **验证码形态要选「滑块验证」或「一点即过」，不要选「无痕验证」**。
> 无痕形态首次初始化不渲染图形验证码（官方 FAQ Q9：`CaptchaType` 为 `TRACELESS`），
> 静默判定失败时直接返回「验证失败，请刷新」，无法降级到人工验证，
> 不适合「必须通过才发短信」的场景。
>
> ⚠️ 两个值容易搞反：
> - **身份标(prefix)** 在「概览」页，用于拼出 `{prefix}.captcha-open.aliyuncs.com`
> - **场景ID(SceneId)** 在「验证场景」列表的「场景名称/ID」列
>
> 填反了会在浏览器里报 `IllegalScene: The scene is invalid`，验证码弹窗不出现。
> 排查方法：打开控制台看 `{prefix}.captcha-open.aliyuncs.com` 的返回，
> 若为 `{"Code":"Success",...}` 则两值正确。

> 除验证码外，另有全站每 10 分钟发送总量上限（默认 20 条）作为成本兜底。

### 需要说明的边界

以上措施能挡住随手的脚本和常规爬虫，但**挡不住有大量代理池且愿意投入的人**。
公开检索类服务的本质决定了这一点：接口必须能被正常浏览器调用，就无法在协议层
完全区分人与脚本。上述分层的作用是把「357 次请求拖走全库」变成
「需要多个 IP、多天、且被反复封禁」，让成本远高于收益。

真要再往上加，只剩登录态一条路（会伤正常用户的检索体验）。验证码已做成渐进式，只挡异常流量。
